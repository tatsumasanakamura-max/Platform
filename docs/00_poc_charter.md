# PoC憲章

## 目的

個人開発・Firebase Blazeプランの無料利用枠を意識した制約下で、Codexを開発主体とし、要件整理、設計、実装、テスト、文書更新、変更影響分析を一貫して行うAI Native開発方式によって、柔軟で保守しやすい銀行カードローン申込フォームのプロトタイプを構築できるか検証する。

## 前提

- CHR-01: 業務外の個人開発であり、銀行・企業からの正式受託ではない。
- CHR-02: 開発者1名がPoCオーナー、実装者、最終判断者を兼ね、Codexが主な作業主体となる。
- CHR-03: 仮想銀行、仮想商品、合成データ、APIスタブだけを使用する。
- CHR-04: 本番導入、実銀行接続、実顧客利用、本番認定を目的としない。
- CHR-05: Blazeプランを使用するが月額0円を目標とし、サービス追加前に課金可能性を人間が確認する。

## 検証テーマ

| ID | テーマ | 指標 |
|---|---|---|
| OBJ-01 | Codex主体で動作アプリを完成できる | KPI-01 |
| OBJ-02 | 要件から定義・コード・テスト・文書を一貫生成できる | KPI-04,06 |
| OBJ-03 | 項目や分岐を少ない作業で変更できる | KPI-02,03 |
| OBJ-04 | 自動テストで既存機能を守れる | KPI-05,07 |
| OBJ-05 | 2商品目・別銀行差分を小さく追加できる | KPI-08,09 |

| OBJ-07 | スマートフォンで迷いにくいUIを作れる | KPI-11,12 |

## 成功条件

- PoC-1の15〜25項目、3〜5分岐、確認・完了までがスマートフォンで動く。
- フォーム定義、限定ルール、コード、テスト、文書がGitで追跡される。
- 同じ入力に対するルール結果がブラウザとNode.jsテストで一致する。
- 代表変更を行い、回帰テストで意図しない破壊を検出できる。
- 実データ・秘密情報を扱わず、画面とREADMEに「本番利用不可」を表示する。
- 作業時間とCodex／人間の修正内容を簡易worklogに残す。

## 代替統制

多人数承認は行わない。Codexの自己レビュー、自動テスト、人間の差分レビュー、可能ならCodexの別会話・別ターンによる文脈を切ったレビューで代替する。単独評価の限界は結果に明記する。

## 縮小条件

作り込みがPoC-1完成を妨げる、料金見込みが事前説明なく増える、実データが必要になる、またはルール定義が個別コードより複雑になる場合は対象を縮小する。
