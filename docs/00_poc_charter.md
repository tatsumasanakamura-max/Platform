# AI Native銀行カードローン申込プラットフォーム PoC憲章

## 1. 文書目的

本書はPoCの目的、成功条件、統制、意思決定境界を定める。対象範囲は [01_scope.md](01_scope.md)、評価方法は [10_poc_evaluation_plan.md](10_poc_evaluation_plan.md) を正とする。

## 2. 背景と解くべき問題

銀行・商品別の個別実装により、制度・商品変更時の影響範囲が広く、仕様・実装・テストの同期、変更速度、担当者交代に課題がある。本PoCでは、フォーム定義を「実行可能な仕様」とし、AIを開発ライフサイクルへ組み込む方式が、品質・統制を損なわず課題を改善できるかを検証する。

## 3. 目的と成功仮説

| ID | 目的 | 検証仮説 | 主評価指標 |
|---|---|---|---|
| OBJ-01 | 開発生産性向上 | 要件から定義・テストの草案をAI生成し、動作版までを短縮できる | MET-01, MET-02 |
| OBJ-02 | 保守・変更速度向上 | 項目・文言・ルール・マッピングの多くを定義変更で完結できる | MET-03, MET-04, MET-09 |
| OBJ-03 | 銀行・商品差分への柔軟性 | 共通ランタイムとバージョン付き差分定義で横展開工数を抑えられる | MET-10 |
| OBJ-04 | 一貫性とテスト品質向上 | 同一定義から実行・説明・テストを生成し、不一致と未検証分岐を削減できる | MET-05, MET-07, MET-08 |
| OBJ-05 | 属人化軽減 | 変更影響と検証結果を機械可読にし、新規担当者が安全に変更できる | MET-06, MET-11 |
| OBJ-06 | UX改善高速化 | 計測可能なスマホUIと定義駆動変更で離脱仮説を迅速に検証できる | MET-03, UX指標 |

## 4. PoC成功条件

- シナリオA〜Dを同一の共通ランタイム上で実施できる。
- `bank_id`、`product_id`、`form_version` で公開定義と申込セッションを特定できる。
- 重要判定は決定的プログラムが行い、AI推論は本番申込判定経路に存在しない。
- AI生成物はスキーマ検証、静的検証、自動テスト、差分レビュー、人間承認を通過しなければ公開できない。
- 目的と要件、テスト、評価記録を追跡できる。
- 定量目標はベースライン測定後に承認する（暫定目標は [10_poc_evaluation_plan.md](10_poc_evaluation_plan.md)）。

## 5. ガバナンス

| ID | 決定領域 | Accountable | PoCでの扱い |
|---|---|---|---|
| GOV-01 | 商品・審査・法令要件 | 銀行業務責任者／法務・コンプライアンス | AIは草案のみ。人間承認必須 |
| GOV-02 | セキュリティ・個人情報 | セキュリティ責任者／個人情報管理責任者 | 脅威分析とデータ取扱い承認必須 |
| GOV-03 | UX・アクセシビリティ | プロダクト責任者 | ユーザーテストとWCAG確認 |
| GOV-04 | アーキテクチャ・リリース | テックリード | 自動ゲート通過後に承認 |
| GOV-05 | PoC評価 | PoCオーナー | 証跡を凍結し、再現可能に集計 |

## 6. 前提・制約

- 仮定 A-01: PoCは本番個人情報を扱わず、合成データまたは匿名化済みデータのみを使う。
- 仮定 A-02: 審査システムはスタブを用い、与信判断自体はPoC対象外とする。
- 仮定 A-03: 比較対象は、同等要件を通常のコード中心方式で行う実績または統制された対照作業とする。
- 制約: PoCの成果をそのまま本番認定しない。本番化には法務、審査、セキュリティ、可用性、運用、外部接続の別審査が必要。

## 7. 終了判定

PoCオーナーは、全シナリオの証跡、指標、重大不具合、未決事項をレビューし、「本番化検討へ進む」「追加PoC」「中止」のいずれかを決定する。判断基準の変更は事前登録し、評価後の恣意的変更を禁止する。
