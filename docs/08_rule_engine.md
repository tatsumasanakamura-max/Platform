# ルール評価

## 方針

PoC-1では汎用DSLを作りすぎない。式は型付き・副作用なしとし、外部I/O、現在時刻、乱数、AI、任意コード、任意正規表現を使わない。同一の定義と入力は常に同一結果にする。

## 対応演算子

| ID | 演算子 |
|---|---|
| OP-01 | `equals` |
| OP-02 | `notEquals` |
| OP-03 | `in` |
| OP-04 | `exists` |
| OP-05 | `greaterThanOrEqual` |
| OP-06 | `lessThanOrEqual` |
| OP-07 | `and` |
| OP-08 | `or` |
| OP-09 | `not` |

暗黙の型変換を避け、nullと未回答を区別する。

## 対応ルール種別

| ID | 種別 | 出力 |
|---|---|---|
| RULE-01 | `visibility` | 表示するか |
| RULE-02 | `required` | 必須か |
| RULE-03 | `validation` | 有効か・エラーコード |
| RULE-04 | `navigation` | 次のセクション |

`derivation`、複雑な日付計算、汎用マッピング条件、優先度競合解決はPoC-2以降の候補とする。

## 評価順

1. 入力を定義された型へ変換する。
2. visibilityを評価する。
3. requiredを評価する。非表示項目は必須にしない。
4. validationを評価する。
5. セクション完了時にnavigationを評価する。

## テスト

- RET-001: Unitテストで各演算子のtrue/false/nullを確認する。
- RET-002: 数値や文字数の境界直前・境界・直後を確認する。
- RET-003: 3〜5件の実例について代表経路を確認する。
- RET-004: ブラウザとNode.jsで同じ関数・テストベクトルを使う。
- RET-005: 変更後に全テストを再実行し回帰成功率を記録する。

MC/DC、ミューテーションテスト、網羅的な組合せ生成はPoC-1の完了条件にしない。

## 本番との差

クライアント評価は改ざん可能であり、本番の最終検証には使えない。本番では信頼できるサーバーで同じルールを再評価する。PoCでFunctionsを採用する場合は、この境界を小規模に検証できる。
