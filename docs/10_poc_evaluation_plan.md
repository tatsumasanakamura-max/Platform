# PoC評価計画

## 1. 評価設計

Scenario A〜Dを `scenario_run_id` 単位で実施する。開始前に要件、入力データ、完了条件、担当者、環境、ツール版を凍結する。可能なら同等経験の担当者による従来方式の対照実施、難しい場合は直近類似案件の実績値を正規化して比較する。比較方法の差は必ず注記する。

## 2. 共通イベント

工程イベントは `event_id, scenario_run_id, change_request_id, actor_type, actor_id_pseudonym, event_type, timestamp, artifact_id, artifact_hash, tool_version` を持つ。工数はタイマーだけでなく、作業セッションの開始・終了と除外時間を記録する。

## 3. 指標定義

| ID | 指標・計算式 | データ源／ログ | 比較基準 | 記録 |
|---|---|---|---|---|
| MET-01 | 要件確定→動作可能版の経過時間 | `requirement_approved` と `env_smoke_passed` の時刻 | 従来対照の中央値 | pipeline events |
| MET-02 | 人手実装工数 = coding + config + test authoring + docs（レビュー除外値も併記） | worklog、PR活動、作業分類 | 従来対照の人時 | worklog.csv |
| MET-03 | 変更要求→検証環境反映の経過時間 | `change_accepted`〜`deployed_test` | 変更種別別の対照 | pipeline events |
| MET-04 | コード変更なし割合 = 定義のみで完了した変更件数 / 全変更件数 | diff分類、change manifest | Scenario B/C/Dと従来方式 | git diff metadata |
| MET-05 | AI生成変更の初回テスト合格率 = 初回候補で必須ゲート全合格 / AI生成変更数 | generation record、CI run | シナリオ・変更種別別 | generation ledger + CI |
| MET-06 | 人間修正率 = 人間変更行/AI初稿変更行（定義・コード・テスト・文書別）。棄却率も併記 | artifact hash、diff provenance | 変更種別別 | provenance report |
| MET-07 | ルールカバレッジ = 実行済み決定表行/全行、経路、真偽結果、境界値、mutation score | test report、rule manifest | 目標: 決定表行100%、重要経路100% | coverage.json |
| MET-08 | 不一致件数 = 検証で確認された仕様/定義/実装/テスト不一致 | INC台帳、自動整合性レポート | 従来対照、重大度別 | inconsistencies.csv |
| MET-09 | 既存機能デグレード件数 | 回帰テスト失敗をトリアージし既存期待の破壊と認定した件数 | 各変更シナリオ、重大度別 | defect tracker |
| MET-10 | 2商品目・別銀行追加工数 | Scenario C/DのMET-01/02と差分ファイル数 | 商品1新規構築、従来対照 | scenario summary |
| MET-11 | 新規担当者が変更できるまでの時間 | briefing開始〜独力で小変更をゲート合格 | 従来オンボーディングまたは複数参加者 | onboarding log |

## 4. 補助指標

- UX: セクション離脱率、完了率、完了時間、項目別初回エラー率、エラー回復率、再開成功率。
- 品質: escaped defect、レビュー指摘数、重大脆弱性、アクセシビリティ違反。
- AI運用: 生成時間、再生成回数、棄却理由、モデル別固定評価スコア、推論コスト。
- 保守性: 変更ファイル数、影響コンポーネント数、定義差分比率、循環的複雑度（コード変更時）。

UX指標はPoC参加者とサンプルが限られるため、製品KPIの改善を断定せず操作上の兆候として扱う。

## 5. 動作可能版の定義

対象受入条件が検証環境で動作し、必須自動ゲートが合格し、代表E2Eが完了し、重大既知欠陥がなく、版と証跡が固定された時点。人間承認前のプレビューは含めない。

## 6. 暫定成功目標

ベースライン取得前の仮説値であり、開始前に承認する。

| ID | 暫定目標 |
|---|---|
| TAR-01 | MET-01、MET-02、MET-03が比較基準から30%以上改善 |
| TAR-02 | Scenario BのMET-04が60%以上 |
| TAR-03 | MET-05が70%以上、重大な安全ゲート逸脱0 |
| TAR-04 | MET-07の決定表行・重要経路100%、mutation score目標は試行後確定 |
| TAR-05 | 重大不一致・重大デグレード0、総不一致は対照以下 |
| TAR-06 | Scenario C/Dの人手工数がScenario Aの各50%以下 |
| TAR-07 | 新規担当者が1営業日以内に指定小変更をゲート合格 |

## 7. バイアスと再現性

- 同一要件・同一受入テストを比較方式へ使用する。
- AI方式だけが要件改善の恩恵を受けないよう、確定要件を両方式へ渡す。
- 学習効果を記録し、シナリオ順を固定するか可能なら担当を交差させる。
- 待ち時間と実作業時間を分ける。
- AI失敗、手動回避、再実行も除外せず記録する。
- 生ログを保持し、集計スクリプト・版・除外規則を固定する。

## 8. シナリオ別測定

| Scenario | 主な計測 | 固有の比較 |
|---|---|---|
| A 新規 | MET-01/02/05/06/07/08 | 従来新規構築 |
| B 変更 | 全変更ごとMET-03/04/05/06/09 | 変更種別別従来実績 |
| C 2商品目 | MET-01/02/04/07/10 | Scenario A比、従来商品追加 |
| D 別銀行 | MET-01/02/04/07/10 | Scenario A比、従来銀行展開 |

## 9. 判定会議

PoCオーナー、業務、UX、技術、QA、セキュリティが証跡をレビューする。暫定目標未達でも原因が明確な場合は追加PoCを選べるが、重大な判定委譲、PII漏えい、監査不能、ゲート迂回があれば本番化検討へ進めない。
